# 연구 계획 개요 — 범용 코딩 에이전트의 EDA 하네스 설계 연구

작성: 2026-08-25 · 대상 독자: Operator (확정 계획의 평문 설명)
원천 문서: [`research-tree.yaml`](../research-tree.yaml) · [`experiments/H1-harness/protocol.md`](../experiments/H1-harness/protocol.md) · [`issues/001`](../issues/001-hypothesis-judgment-brief.md)

## 1. 무엇을 연구하는가

**질문**: "Claude Code 같은 범용 코딩 에이전트에게 어떤 보조 장치(하네스)를 어떻게 만들어 주면, 칩 설계 플로우(RTL→GDS)를 혼자서 끝까지 완주하는 능력이 얼마나 좋아지는가?"

여기서 **하네스(harness)**란 에이전트에게 장착하는 EDA 특화 보조물 일체를 말한다: 플로우 실행 절차를 담은 스킬 파일, 툴 로그 해석 가이드, 실패 시 복구 전략, 단계별 체크리스트 등. 모델 자체는 그대로 두고 **주변 장치만** 바꾸는 것이 핵심이다.

## 2. 왜 이 주제인가 (근거)

제로베이스 문헌 조사(5축 46편, [`literature/survey.md`](../literature/survey.md))에서 확인된 사실:

1. **작은 RTL 모듈 생성은 이미 풀린 문제**다 — 기존 벤치마크는 95%+ 포화. 반면 실제 플로우 전체(설계→검증→합성→배치배선→sign-off)는 SOTA도 30% 안팎.
2. **FluxBench(2026)의 발견**: 같은 모델이라도 에이전트 하네스 구조에 따라 성능이 86%까지 갈렸고, 맨몸의 Claude Code는 전용 시스템에 최대 8.4배 뒤졌다.
3. 그런데 "**하네스를 어떻게 설계해야 하는가**"를 체계적으로 연구한 논문은 없다 — 명확한 공백.
4. 완주율·QoR·Token ROI라는 **공인 비교 지표**가 이미 있어, 1인 연구자도 측정 가능한 기여를 할 수 있다.
5. 실험 전체가 오픈소스 툴(LibreLane, SKY130 PDK) + 로컬 CPU + 구독 CLI로 돌아간다 — 프로젝트 제약과 정합.

## 3. 가설 트리 (승인 상태)

| ID | 주장 | 상태 |
|---|---|---|
| **H1** | 잘 설계한 하네스를 달면 RTL→GDS 완주율이 baseline 대비 **2배 이상** 오른다 | 승인 · **protocol LOCKED** |
| H1.1 | 하네스 설계에 따라 Token ROI(토큰당 품질)가 2배 이상 갈린다 | 승인 (H1에 얹어 측정) |
| H2 | 만든 엔진과 다른 엔진이 검사하는 "교차 검증"이 자기 검증보다 버그를 더 잡는다 | 승인 · H1 인프라 완성 후 |
| H4 | 기능 테스트를 통과한 AI 생성 RTL도 상당수가 sign-off(제조 가능 판정)에서 탈락한다 | 승인 · H1 인프라 완성 후 |
| H5 | AI 협업 설계에서 "완성했다"와 "이해했다"는 별개다 (N=1 종단 사례) | 승인 · 경량 병행 |
| H3 | Tiny Tapeout 공개 설계로 오염-내성 평가셋을 만들 수 있다 | 보류 (novelty 재조사 필요) |
| H6 | LLM 에이전트가 플로우 파라미터 튜닝을 기존 도구보다 잘한다 | 연기 |

순서에 담긴 논리: **H1의 실험 인프라(로컬 RTL→GDS 플로우 + 자동 채점 + 토큰 계측)가 H2·H4·H5의 기반을 겸한다.** 어떤 순서로 가든 이 인프라가 선행 투자이므로, 공백이 가장 명확한 H1부터 소진한다.

## 4. H1 실험 설계 (LOCKED — 요지)

### 비교 구도
- **B0 (baseline)**: 맨몸의 Claude Code. EDA 관련 스킬·지침 전혀 없음.
- **T1 (하네스)**: B0 + 사전 커밋된 EDA 하네스.
- 같은 모델·같은 버전·같은 태스크 프롬프트. 시행마다 새 세션. 인간 개입 0.

### 태스크 3종 (난이도 사다리, 전부 SKY130 + LibreLane 로컬)
| # | 태스크 | 왜 이 난이도인가 |
|---|---|---|
| A1 | 파라미터 변형 UART (스펙 문서 → RTL → 테스트벤치 → GDS) | 단일 모듈 기본기 |
| A2 | SPI 마스터 + FIFO 통합 | 멀티모듈 — 문헌상 SOTA가 무너지기 시작하는 지점 |
| A3 | PicoRV32 축소판 hardening (RTL은 주고 제약 충족 GDS까지) | 백엔드 중심, FluxBench 대표 계열 |

"성공"의 정의는 사람이 아니라 **결정적 채점 스크립트**가 판정한다: GDSII 생성 + DRC 위반 0 + 타이밍(STA) 위반 0. 학습 데이터 오염을 피하려고 공개 스펙을 그대로 쓰지 않고 비트폭·상수를 변형해 쓴다.

### 2단계 구조 — Phase A는 "판정"하지 않는다
- **Phase A (스모크, 18세션 = 3태스크 × 2조건 × 3시행, 7일)**: 환경이 성립하는지, baseline이 이미 잘해서 개선 여지가 없는 건 아닌지(headroom), 방향 신호가 있는지만 본다. 결과는 4갈래 중 하나: 환경 무효 / 난이도 상향 후 재설계 / Phase B 진행 / 하네스 재검토.
- **Phase B (본 실험)**: H1의 정식 판정. 판정 규칙은 **지금 이미 고정**되어 있다 — 조건당 15시행 이상, Fisher 검정 p<0.05 **그리고** 완주율 2배 이상일 때만 supported. 유의해도 2배 미만이면 refuted(주장이 "2배"이므로). H1.1은 하네스 변형이 2종 이상인 Phase B에서만 검정.

### 왜 이렇게 까다롭게 하는가
1인 연구는 "하네스 만든 사람 = 실험하는 사람"이라는 구조적 약점이 있다. 이를 보완하는 장치가 셋: ① 판정 기준을 결과 보기 전에 잠그고(git 커밋 순서가 증명), ② 채점은 결정적 스크립트가 하며(생성≠심사), ③ 프로토콜 자체를 다른 엔진(Codex)이 심사했다 — 이번에 4차 왕복 끝에 approve. Codex가 잡아낸 결함(예: baseline이 4/9만 넘어도 2배가 산술적으로 불가능한데 포화 기준이 7/9였던 것)은 실제 설계 버그였다.

## 5. 실행 절차 (다음 액션)

```
[pre-flight — 기한 미기산, 목표 2일]
  LibreLane 환경 구축 → 태스크 스펙·채점기·golden RTL 커밋 → 하네스 커밋
  (이 순서 자체가 증명: 하네스를 채점기에 과적합시킬 수 없음)
        ↓
[실행 개시 커밋] ← 이 순간부터 7일 기산. 모델 ID·환경 버전 고정 기록
        ↓
[세션 실행 4-6일] 하루 최대 6세션, 직렬, 세션당 2시간 상한
        ↓
[집계·게이트 판정·results 커밋] ← plan 커밋과 절대 안 합침
```

## 6. 지켜지는 불변 원칙

- 웹 조사는 exa만 · 생성 엔진 ≠ 심사 엔진 · 구독 CLI만(metered API 금지) · 로컬·무료 컴퓨트만 · 실칩 제작은 사이클 게이트에 불포함 · 객관적 게이트 없는 자율 진행 금지
- 프로토콜에서 벗어나는 모든 분석은 EXPLORATORY 라벨을 달고 기록

## 7. 이 계획이 실패하면

각 실패 모드에도 정보 가치가 있도록 설계됨: baseline 포화 → "이 난이도는 하네스 불필요"라는 한계 지도의 한 칸. 하네스 무효(T1 ≤ B0) → FluxBench 해석에 대한 반례로 기록 가치. 환경 실패 → 재현성 리포트 자체가 오픈소스 EDA 커뮤니티 기여.
