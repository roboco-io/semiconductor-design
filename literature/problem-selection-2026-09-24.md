# 공개 근거로 다시 고른 반도체 업무 문제

작성: 2026-09-24 · 상태: EXPLORATORY · 사용자 조건: 현업 접근 없이 공개 자료로 조사

## 이번 판단

**우선 검증할 문제는 “STDF→ATDF 변환에서 검사 결과의 의미가 어긋나는 문제”로 좁힌다.** STDF는 반도체 검사 결과를 저장하는 형식이고, ATDF는 이를 텍스트로 표현하는 형식이다. 변환 과정에서 재시험 상태를 나타내는 빈 필드가 빠지면 뒤쪽 값의 위치가 달라져 잘못 해석될 수 있다. 첫 대상은 PRR(칩 한 개의 검사 결과 레코드)의 재시험 필드다.

이 선택은 공개 근거만으로 시작할 때의 **검증 우선순위**다. 독립 제품의 수요나 매출, 특정 기업의 도입 의사가 확인됐다는 뜻은 아니다. 기존 라이브러리의 작은 수정으로 충분하면 그 범위에서 해결한다. 별도 검사 도구가 필요한지는 여러 사례와 기존 대안을 대조한 뒤 결정한다.

선정 이유는 세 가지다. 실제 사용자의 구체적인 입력·출력 신고가 있고, 비교할 기존 구현을 공개 소스로 읽을 수 있으며, 생산라인 데이터나 고가 시뮬레이터 없이 의미 보존을 확인할 작은 사례를 만들 경로가 있다. 모델 성능을 개선하는 것보다 이 문제를 더 중요하다고 단정한 것이 아니라, 현재 제약에서 잘못된 선택을 빠르게 걸러낼 수 있다는 판단이다. [공개 신고 R01](https://github.com/Semi-ATE/STDF/issues/58), [수정안 R02](https://github.com/Semi-ATE/STDF/pull/59), [확인한 소스 R03](https://github.com/Semi-ATE/STDF/blob/main/Semi_ATE/STDF/PRR.py)

## 사용자 의도와 조사 범위

사용자는 조사와 해결할 문제 선정부터 다시 진행하도록 요청했고, 현업 접근 경로는 “현재는 없음 — 공개 자료로 조사”라고 답했다. [INTENT](../INTENT.md)의 목표인 반도체 기업에 유용한 SW·모델과 설계·검증·공정·수율·테스트 전 분야 범위는 유지한다. 기존 O2→O3→O7 순위는 지난 조사에서 나온 제안으로 보존한다.

기존 A와 C의 결과에서 가져올 원칙은 “정확한 구현과 업무 효용은 다르다”, “개발 사례와 새로운 사례의 성능은 다르다”이다. 새 후보에도 기존 도구와의 비교, 보지 않은 사례, 수행 주체의 명시가 필요하다. 기존 가설과 LOCKED protocol은 이번 조사에서 변경하지 않는다.

검색 전 질문과 선별 기준은 [issue 003](../issues/003-problem-selection-restart.md)에 기록했다. 직접 문제 근거, 이미 있는 대안, 공개 입력과 정답, 로컬 비용, 업무 판단과의 연결을 비교했다. 미확인은 수치 점수로 감추지 않았다.

## 기존 순위가 달라진 이유

기능의 부재를 가정할 수 없는 근거가 나왔다.

- **커버리지 통합:** pyucis가 이미 Verilator·cocotb-coverage 입력, 변환·병합·리포트를 제공한다. 단순 통합 자체를 공백으로 취급하지 않는다. [R24](https://github.com/fvutils/pyucis)
- **RTL 오류 입력 축소:** sv-bugpoint가 SystemVerilog 입력 축소와 Verilator용 검사 스크립트 생성을 제공하고, Verilator 문서가 이를 안내한다. 새 범용 축소기의 필요성은 별도 입증해야 한다. [R25](https://github.com/antmicro/sv-bugpoint), [R26](https://verilator.org/guide/latest/contributing.html)
- **파형 분석:** wavetools의 필터·diff와 wavekit-mcp의 시간 패턴 질의가 존재한다. 원시 파형을 LLM에 넣는 조건만 이기는 실험은 기존 대안 대비 가치를 보여주지 못한다. [R16](https://github.com/cxzzzz/wavekit-mcp), [R17](https://github.com/hudson-trading/wavetools)
- **공정 예측 신뢰도:** NIST가 공개한 2025년 연구는 이미 온라인 Gaussian process의 불확실성을 이용한 동적 실측 선택을 다룬다. 평균 오차만 비교하거나 정기 실측만 기준선으로 두면 중요한 기존 접근을 누락한다. [R20](https://www.nist.gov/publications/comparative-study-semiconductor-virtual-metrology-methods-and-novel-algorithmic)
- **STDF 비교·재시험 집계:** STDF-Viewer가 파일 병합·비교와 대체된 검사 결과 처리를 제공한다. yieldHUB도 재시험 집계 기능을 설명한다. 따라서 새 범용 뷰어나 집계 대시보드를 먼저 만들 근거는 약하다. [R12](https://github.com/noonchen/STDF-Viewer/releases/tag/V4.0.0), [R11](https://www.yieldhub.com/blogs/stdf-datalog-analysis-taking-rescreen-into-account)

이들은 기능이 존재한다는 근거이며, 모든 사용자의 문제가 해결됐다는 증거는 아니다. 반대로 공개 이슈가 열려 있다는 사실만으로 현재 배포판에서도 버그가 재현된다고 말하지 않는다.

## P1의 근거와 반대 근거

### 재현할 수 있는 문제 진술

“테스트 데이터 도구 개발자가 PRR 레코드를 STDF에서 ATDF로 변환할 때, 재시험을 뜻하는 두 비트가 모두 꺼져 있는 경우에도 비어 있는 재시험 필드의 위치가 유지되는지 확인한다.”

이는 첫 재현 대상이다. 장기 문제는 검사 결과 변환의 의미 보존이지만 첫 조사에서 전체 포맷, 모든 장비, 여러 lot의 재시험 정책까지 다루지는 않는다.

issue #58은 비어 있어야 할 Retest Code 필드 누락을 신고한다. 관련 PR #59는 추출 결과에서 open draft로 보였다. 읽은 `PRR.py`에는 두 비트 중 하나가 켜진 경우 출력하는 분기가 있지만, 모두 꺼진 경우 빈 필드를 출력하는 분기가 보이지 않는다. **이것은 소스 정독으로 얻은 재현 가능성 추론이다. 실제 최신 SHA를 고정한 실행 검증은 아직 하지 않았다.** [R01](https://github.com/Semi-ATE/STDF/issues/58), [R02](https://github.com/Semi-ATE/STDF/pull/59), [R03](https://github.com/Semi-ATE/STDF/blob/main/Semi_ATE/STDF/PRR.py)

### 수정된 문제를 새 공백으로 세지 않는다

issue #65는 읽고 다시 저장한 뒤 판정 정보가 달라지는 사례를 보고했지만, 연결된 비트 순서 수정 PR #66은 2024-12-20에 병합됐다. 따라서 그 비트 오류를 현재 미해결 기능으로 세지 않는다. 파일 크기가 증가한 것도 옵션 필드가 추가로 기록되기 때문일 수 있으므로, 바이트 일치와 의미 일치를 구분한다. [R04](https://github.com/Semi-ATE/STDF/issues/65), [R05](https://github.com/Semi-ATE/STDF/pull/66)

issue #46은 닫혔고 후속 #48에서 blank 값·site 값·판정 플래그 해석이 다시 논의됐다. 어느 라이브러리가 더 많이 동의하느냐만으로 정답을 정하지 않고 원 명세의 해당 조항을 확인해야 한다. 테스트 파일 하나에 skip 표시가 있다는 사실도 현재 버그의 증거로 바꾸지 않는다. [R06](https://github.com/Semi-ATE/STDF/issues/46), [R07](https://github.com/Semi-ATE/STDF/issues/48), [R09](https://github.com/Semi-ATE/STDF/blob/main/tests/test_MPR.py)

### 기업 업무와의 연결은 아직 가설이다

yieldHUB는 lot ID 오타와 run type 표기 오류가 집계에 영향을 준 공급사 사례를 설명한다. 이것은 테스트 데이터의 해석·식별 정보가 업무에 중요하다는 근거다. 공개 Python 라이브러리의 PRR 누락이 같은 기업에서 발생했다거나 같은 손실을 일으켰다는 증거는 아니다. 현업 사용자는 확보되지 않았고, 사람의 시간 절감이나 금전적 효과도 측정하지 않았다. [R10](https://www.yieldhub.com/blogs/standardising-stdf-metadata)

LinqToStdf는 손상 파일 처리·복구·요약 레코드 생성과 필터를, stdfFixer는 불완전 파일의 요약 레코드 복구를 제공한다. 이 기능들을 대조하기 전에는 “STDF 검증 도구가 없다”고 주장할 수 없다. [R13](https://github.com/marklio/LinqToStdf), [R14](https://github.com/noonchen/stdfFixer)

### 현실적인 산출물 선택

| 접근 | 가치가 생기는 조건 | 현재 권고 |
|---|---|---|
| 기존 라이브러리 수정과 재현 테스트 | 최신 버전에서 실제 오류가 재현되고 수정 범위가 작음 | 첫 해결 방식 |
| 여러 변환기의 의미 보존 대조 사례·검사 도구 | 독립 사례와 구현 사이에서 기존 검사로 놓치는 문제가 반복됨 | 조건부 확장 |
| 기업용 테스트 분석 플랫폼 | 대표 생산 데이터·사용자·통합 요구와 기존 제품 대비 가치 확보 | 현재 근거로 착수하지 않음 |

코드 저장소의 MIT 표시는 확인했지만, 이슈 첨부 파일의 재배포 조건까지 확인한 것은 아니다. 우선 소스 라이선스가 적용되는 테스트와 직접 작성한 최소 사례의 경로를 검토한다. 생산 자료를 확보한 것으로 주장하지 않는다. [R08](https://github.com/Semi-ATE/STDF)

첫 관문의 목적은 작은 공개 버그 하나를 큰 제품 수요로 확대하는 일을 막는 것이다. 실행 이후에 주 지표·임계값을 유리하게 바꾸지 않으며, 새 구현의 효과 실험은 기준과 비교자를 먼저 고정한다. 기존 라이브러리 개선이 충분하다면 그 자체를 유용한 산출물로 본다. 외부 이슈 등록이나 PR 제출은 이번 작업에서 수행하지 않았다.

P1이 현재 도구로 해결된 것으로 확인되면 P2의 코드 접근성과 기존 파형 도구 비교를 다음 관문으로 삼는다. P3는 CMP 파일·사용 조건·시간 식별자 확인이 선행된다. 실패한 후보를 살리기 위해 새 지표를 즉흥적으로 만드는 방식으로 진행하지 않는다.

## 조사 방법과 확인 수준

exa 검색 **27회**, 반환 기록 **97건**, 고유 URL **83개**를 확인했다. 동일 URL 중복 14건, 결정 근거 채택 25건, 제외 20건, 이번 판단에 사용하지 않은 배경 자료 38건으로 분류했다. 직접 추출로 추가한 3개 출처를 합쳐 최종 근거는 **28개**다. 관련 자료가 검색됐다는 사실과 결정 근거로 채택했다는 사실을 구분한다.

추가 추출은 9회 호출, URL 요청 24건이며 내용 반환은 23건이었다. WaveformQA 코드 URL 1건은 추출에 실패했고 추가 검색으로도 코드·라이선스 접근을 확인하지 못했다. 전체 응답에서 인용 URL이 없는 검색 응답은 없었다. 반환문과 추출 길이 제한을 넘는 전문을 모두 읽었다고 주장하지 않는다. 원문·URL의 현재 상태는 실제 재현 직전 다시 고정해야 한다.

이 조사는 전 분야의 **탐색적 문제 비교**이며, 학술 데이터베이스 3종을 직접 검색한 체계적 문헌고찰이 아니다. 사용자 인터뷰, 데이터 다운로드, 코드 설치, 재현 실행, 현업 효용 검증은 수행하지 않았다. 기업 발표·공급사 기능·공개 버그·논문 실험은 증거 성격이 다르므로 동일 점수로 합산하지 않았다.

검색어, 자료별 선별 이유, 출처의 확인 수준과 한계는 [원자료 기록](raw/07-problem-selection-search-log.json)에 보존한다. 이번 단계의 결론은 P1 우선 검증이며 새 가설 승인·제품 구현 착수·supported/refuted 판정은 아니다.
