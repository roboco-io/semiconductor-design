# 009 — 도메인 A 알고리즘 태스크 선정 (2026-07-13)

> status: **open** — 구현 plan 착수 전 확정 필요
> 출처: [2026-07-13 피벗 spec §4](../docs/superpowers/specs/2026-07-13-agent-promotion-governance-pivot-design.md)

## 결정 질문

도메인 A(알고리즘 성능 최적화) 루프의 대상 태스크를 무엇으로 하는가?

## 선정 기준 (spec §4 복사 인용)

1. 정합성 판정이 결정적 (테스트로 정답/오답이 갈림)
2. 워크로드 패밀리 6개+ 구성 가능 (dev V + holdout ≥3 + sealed 1)
3. 단일 파일 구현이 수백 줄 이내
4. 실행시간이 로컬에서 초 단위
5. 정직한 개선 여지와 gaming 여지가 공존 (컨트롤 후보 known-good/known-bad 작성 가능)

## 후보 (spec에서 예시된 계열)

- **bin packing 휴리스틱** — first-fit/best-fit 참조 구현 대비 개선 여지 큼, 입력 분포(균등/편중/
  대형 아이템 비중)로 패밀리 구성 자연스러움. 단 "성능"이 실행시간인지 packing 품질인지 지표
  단일화 필요(spec 지표는 실행시간 — 품질은 정합성 제약으로 두는 방안 검토).
- **정규식 매칭 / 문자열 검색** — 실행시간 지표가 자연스럽고 패턴·텍스트 유형으로 패밀리 구성.
  gaming(입력 캐싱) 여지 풍부.
- **그래프 휴리스틱** (최단경로 전처리, 그래프 유형별 패밀리) — 구조 다양성 좋음, 구현이 커질 위험.

## 미결 세부

- 지표 단일화: 실행시간 단독 vs "정합성(및 품질 하한) 제약 + 실행시간" — spec은 후자 구조
  (정합성 통과 전제 + 실행시간). 품질 지표가 연속적인 태스크(bin packing)는 하한 고정 필요.
- dev/holdout/sealed 패밀리 수 배분 (V는 §4 조건상 ≥2).
- 참조 구현 출처 (직접 작성 vs 표준 라이브러리 대비).

## Decision Brief (2026-07-15)

### 기준별 비교 (spec §4 기준 ①~⑤)

| 기준 | A. 다중 패턴 문자열 검색 | B. bin packing 휴리스틱 | C. 그래프 휴리스틱 |
|---|---|---|---|
| ① 정합성 결정적 | ◎ 매치 위치를 `re`/`str.find` 오라클과 정확 일치 비교 | ○ 유효 배치 검사는 결정적이나 **품질 하한(빈 수 ≤ 참조)을 정합성에 추가**해야 함 | ○ 거리값 일치로 결정적 |
| ② 패밀리 6개+ | ◎ 패턴 수·길이 × 텍스트 유형(자연어/로그/DNA/반복성)으로 풍부 | ◎ 입력 분포(균등/편중/대형 아이템 비중 등) | ○ 그래프 유형(격자/랜덤/스케일프리/도로망) — 생성 코드가 커짐 |
| ③ 단일 파일 수백 줄 | ◎ naive 참조 수십 줄, 개선 구현도 컴팩트 | ◎ first-fit 참조 ~50줄 | △ 최단경로+전처리는 수백 줄 초과 위험(spec에 이미 명시) |
| ④ 로컬 초 단위 | ◎ 텍스트 크기로 조절 | ◎ 아이템 수로 조절 | ○ 가능하나 그래프 생성 비용 별도 |
| ⑤ 개선·gaming 공존 | ◎ 정직: Boyer-Moore/Aho-Corasick/Rabin-Karp 등 고전 알고리즘 공간 넓음. gaming: dev 텍스트 해시 캐싱·결과 하드코딩 | ○ 정직 개선이 자료구조 가속(정렬·구간 트리)에 한정되는 경향. gaming: 입력 시그니처 캐싱 | ○ 양방향 탐색·힙 개선. gaming 가능 |

### 선택지 A — 다중 패턴 문자열 검색 (정규식 계열의 스코프 축소판, 권장)

**Summary**: 텍스트 T에서 패턴 집합 P의 모든 출현 위치를 찾는 solver. full 정규식 엔진 대신
**고정 문자열 다중 패턴 검색**으로 좁혀 ③(구현 규모)과 ①(오라클 단순성)을 동시 확보.
정합성 오라클 = 표준 라이브러리(`re.finditer` 등)와 위치 집합 정확 일치. 참조 구현 =
직접 작성 naive 이중 루프(순수 Python — 오라클과 분리, C 구현과 속도 비교 문제 회피).

**Pros**: 지표가 실행시간 **단독**으로 깔끔(품질 차원 없음 → spec §4 "정합성 통과 전제 +
실행시간" 구조와 정확히 일치, 미결 세부 1 자동 해소). known-good(Aho-Corasick류)·
known-bad(dev 텍스트 캐싱) 작성이 자명. 패밀리 축이 2개(패턴·텍스트)라 6+ 구성 여유.
**Cons**: 스코프(고정 문자열로 제한)를 plan에서 명시해야 함. 고전 알고리즘이 잘 알려져
있어 에이전트가 1세대에 최적해 도달 → 5세대 개선 서사가 빨리 소진될 가능성.

### 선택지 B — bin packing 휴리스틱

**Summary**: first-fit 참조 구현 대비 실행시간 개선. 품질(빈 수)은 정합성 제약으로 고정
(빈 수 ≤ 참조 구현 결과).

**Pros**: 참조 구현·패밀리 구성이 가장 단순. NP-hard 휴리스틱이라 서사가 풍부.
**Cons**: 품질-시간 이중 차원 → 정합성 테스트에 품질 하한을 넣는 설계 부담(미결 세부 1이
그대로 남음). "같은 품질을 더 빠르게"의 정직 개선 공간이 자료구조 트릭 위주로 좁음 —
5세대 동안 개선 여지가 조기 고갈될 위험이 A보다 큼.

### 선택지 C — 그래프 휴리스틱 (최단경로 전처리)

**Summary**: 그래프 유형별 패밀리에서 최단경로 질의 실행시간 개선.

**Pros**: 구조 다양성이 가장 큼, LOGO(패밀리 일반화) 검정력이 높음.
**Cons**: 구현 규모가 기준 ③을 위협(spec 자체가 "구현이 커질 위험" 명시). 벤치 생성
코드까지 frozen 자산으로 관리할 범위가 가장 큼. 1인 Operator 리소스에 과대.

### 권장

**A**. 기준 5개 전부 ◎이고, 미결 세부 1(지표 단일화)이 태스크 성질상 자동 해소된다.
B는 차선(이중 지표 설계 부담), C는 기준 ③ 위반 위험으로 비권장.

**A 확정 시 부속 제안** (plan에서 검증·확정):
- 패밀리 G=7: dev 2 + holdout 4 + sealed 1 (§4 조건 V≥2·H≥3·sealed 1 충족, holdout 여유 1).
- 참조 구현 = 직접 작성 naive 순수 Python(frozen). 정합성 오라클 = 표준 라이브러리 교차검증.
- known-good = Aho-Corasick 또는 Boyer-Moore 계열. known-bad = dev 텍스트 해시 → 사전
  계산 결과 반환 캐싱.

## 해소 경로

구현 plan(`writing-plans`) 착수 전, 태스크 1개 + 패밀리 분할 + 참조 구현을 확정해 본 issue를
resolved로 갱신하고 plan에 반영한다.
