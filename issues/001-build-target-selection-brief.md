## 전제 (Operator 의도)

"반도체 설계에 유용한 소프트웨어 또는 모델을 바이브 코딩 기법으로 개발" — 산출물의 실용성이 목적, 바이브 코딩은 방법. 유용성은 객관 지표(외부 벤치마크 > 채택 증거 > 시간 절감 표)로 검증한다.

## 선택지

### A. H1→H1.1: 실험 추적 도구 + QoR 예측기 로드맵 (권장)
**무엇**: ① "하드웨어판 MLflow" — ORFS/LibreLane run 디렉토리·METRICS2.1 JSON을 자동 수집해 run 목록·PPA 디프·파라미터-결과 상관을 보여주는 로컬 대시보드+CLI. ② 그 데이터로 학습하는 tabular QoR 조기 예측기(XGBoost)를 조기중단 추천 기능으로 통합.
- **Pros**: ① 공백이 도구 전수 비교로 확인됨(어느 기존 도구에도 없음) ② "소프트웨어(도구)+모델(예측기)"를 하나의 로드맵으로 — Operator 의도의 두 갈래를 모두 충족 ③ 도구가 모델의 학습 데이터를 만드는 자기 강화 구조 ④ 도그푸딩 자연스러움(우리 자신이 flow 실험을 하게 됨) ⑤ 예측기는 EDA-Schema 공개 베이스라인과 동일 프로토콜 비교 가능 — 객관 검증 최상
- **Cons**: ① 수요 근거가 B보다 간접적(명시 이슈보다 수작업 사례 기반) ② 채택 확보에 시간 필요 ③ 예측기 학습 데이터를 자가 생성하려면 flow run 수십-수백 회(로컬 CPU 시간) 필요

### B. H2: STA 리포트 분석기 ("타이밍 리포트의 Surfer")
**무엇**: OpenSTA/OpenROAD 타이밍 리포트 → 구조화 JSON + HTML 시각화(slack 히스토그램·경로 드릴다운), CLI+MCP 서버 겸용.
- **Pros**: ① 수요 근거 최강 — 코어팀 이슈 4건 + openroad-mcp가 "Impact: High" 명시 ② 검증이 가장 결정적(golden diff 100%) ③ AI 타이밍 클로저 흐름의 전제 부품이라 시류 정합 ④ 범위가 명확해 최단 기간 첫 릴리스
- **Cons**: ① OpenROAD 코어팀/커뮤니티가 직접 만들 가능성(이슈가 공개된 만큼 선점 리스크) ② 단품 도구 — 모델 트랙으로의 확장성이 A보다 약함 ③ 파서가 툴 버전에 종속(유지보수 부담)

### C. H3: 플로우 실패 진단기 (log doctor)
**무엇**: 실패한 런 디렉토리를 읽어 알려진 실패 시그니처(라우팅 크래시·PDN 훅·LVS 미전원 셀·안테나 반복)를 매칭, 원인·수정 config 제안.
- **Pros**: ① 최대 페인포인트("거의 모두가 겪음") ② 메인테이너 본인이 요청(#7482) ③ Slack/Discord에 흩어져 소실되는 진단 지식을 자산화
- **Cons**: ① 실패 사례 코퍼스 수집이 선행 투자(수요 대비 착수 비용 큼) ② 진단 적중률 검증의 설계 난도 ③ 제안 정확성 오류 시 신뢰 훼손 리스크

### D. H4/H5: 검증 관리 도구 또는 IR drop 경량 모델
**무엇**: 회귀 triage·커버리지 통합(H4) 또는 ICCAD'23 IR drop 리더보드 경량 모델(H5).
- **Pros**: H4 — cocotb 설문 최다 불만 직격. H5 — 공개 리더보드로 객관 비교 최상, 순수 모델 트랙.
- **Cons**: H4 — 신생 경쟁(xevdb·TraceWeave)·UCIS 학습 비용. H5 — "유용한 도구" 의도와 정합 간접적(리더보드 성능 ≠ 실무 채택), 기존 참가작 대비 novelty 제한.
