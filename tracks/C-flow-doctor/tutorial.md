# 트랙 C 튜토리얼 — 칩 만들기가 실패했을 때, "닥터"를 불러보았다

## ① 이야기: 오븐 속에서 무너진 케이크

빵집을 하나 상상해 보세요. 밀가루를 반죽하고, 모양을 잡고, 오븐에 굽고,
마지막에 포장까지 해야 케이크 하나가 완성됩니다. 그런데 어느 날, 오븐을 열어 보니
케이크가 폭삭 주저앉아 있었습니다. 왜일까요? 반죽에 베이킹파우더를 빼먹었을 수도 있고,
오븐 온도가 틀렸을 수도 있고, 굽는 도중에 오븐 문을 벌컥 열었을 수도 있습니다.
망하는 방법은 정말 여러 가지이고, 겉모습(주저앉은 케이크)만 봐서는 이유를 알기 어렵습니다.

칩(반도체)을 설계하는 일도 똑같습니다. 설계 코드를 넣으면 여러 단계를 거쳐
칩 도면이 나오는 "자동 빵 공장" 같은 프로그램이 있습니다. LibreLane, ORFS 같은
오픈소스 도구들인데, 이 공장이 중간에 멈추는 일이 아주 흔합니다. 실제로 한
유명 프로젝트의 게시판에는 "거의 모든 사람이 이 실패를 겪는다"는 글이 올라와
있을 정도입니다. 문제는, 왜 멈췄는지 알려주는 친절한 설명이 별로 없다는 것.
해결 방법은 게시판과 채팅방 여기저기에 흩어져 있다가 잊혀집니다.

그래서 우리는 실험을 하나 했습니다. "실패의 흔적(로그)을 읽고 병명을 알려주는
의사 프로그램을 만들 수 있을까?" 이 의사의 이름은 **flow doctor**,
우리의 세 번째 가설 **H3**입니다.

결말을 먼저 살짝 말하면 — 이 의사는 연습 시험에서 만점을 받고,
진짜 시험에서 0점을 받았습니다. 그런데 이 0점이 생각보다 값진 0점이었습니다.
왜 그런지, 차근차근 이야기해 볼게요.

## ② 핵심 개념: 빵집 비유로 푸는 칩 공장 용어들

### 플로우, 그리고 망하는 여러 가지 방식

**칩 설계 플로우**는 케이크 레시피의 단계 목록입니다. 순서대로 진행되고,
각 단계에서 실패하면 망하는 모양도 다릅니다.

- **합성(synthesis)** — 레시피 글을 실제 재료 목록으로 바꾸는 단계입니다.
  "설탕 두 컵"이라고 썼는데 창고에 설탕이 없으면 여기서 멈춥니다.
  실제 사례로, 설계 코드에서 전선 굵기(포트 폭)가 서로 안 맞아 실패한 경우(C-001),
  같은 재료를 목록에 두 번 적어서 — 같은 모듈을 두 파일에 정의해서 — 실패한
  경우(C-003), 반죽이 너무 커서 주방(메모리)이 감당 못 하고 요리사가 쓰러진
  경우(C-002, 메모리 부족으로 프로세스가 강제 종료됨)가 있었습니다.
- **배치(placement)** — 오븐 팬 위에 쿠키 반죽을 하나씩 올려놓는 단계입니다.
  팬이 너무 작으면 쿠키끼리 붙어 버리죠. 칩에서도 부품을 놓을 자리가
  모자라면 여기서 실패합니다.
- **배선(routing)** — 놓인 부품들 사이를 전선으로 잇는 단계입니다.
  좁은 골목에 전선이 몰리면(혼잡도 초과) 길을 낼 수 없어 실패합니다.
- **LVS**(Layout vs Schematic) — **설계도와 실물을 나란히 놓고 대조하는 검사**입니다.
  "레시피에는 딸기 5개라고 했는데 실제 케이크엔 4개네?" 하고 잡아내는 검수원이죠.
- **DRC**(Design Rule Check) — **공장의 안전 규칙 검사**입니다. "전선끼리 최소
  이만큼은 떨어져야 한다" 같은 공장(파운드리)의 규칙을 어겼는지 봅니다.
  소방 점검관이 "복도에 물건 쌓지 마세요"라고 지적하는 것과 같습니다.
- **안테나 위반** — 칩을 만드는 도중에 긴 전선이 **정전기를 빗물받이처럼 모아서**
  연약한 부품(트랜지스터의 게이트)을 태워 버리는 문제입니다. 겨울에 문손잡이를
  잡다 찌릿한 그 정전기가, 아주 작은 부품에게는 벼락인 셈입니다.
- **PDN**(전원 분배망) — 칩 구석구석에 전기를 보내는 **수도 배관**입니다.
  배관이 안 닿는 방이 있으면 그 방의 부품은 작동을 못 합니다.

### 진단에 필요한 개념들

- **로그(log)** — 요리하는 동안 옆에 적어 두는 **요리 일지**입니다.
  "오후 3시, 반죽이 이상하게 묽음" 같은 기록이죠. 플로우가 멈추면
  이 일지 끝에 에러 메시지가 남습니다. 우리의 의사는 이 일지만 읽고
  병명을 맞혀야 합니다.
- **진단 룰(rule)** — 의사의 **증상-병명 대응표**입니다. "열이 나고 목이 아프면
  감기"처럼, "로그에 이 문장이 있으면 원인은 이것, 처방은 이것"이라고
  미리 적어 둔 표입니다. 우리는 이런 표를 33개 만들었고, 표마다
  근거가 된 원본 사례의 링크를 반드시 달았습니다.
- **과적합(overfitting)** — **연습문제집만 달달 외운 학생**입니다.
  문제집의 답은 다 맞히지만, 시험에 처음 보는 문제가 나오면 손도 못 댑니다.
  이해한 게 아니라 답을 암기했던 것이죠.
- **홀드아웃(holdout)** — 그래서 필요한 것이 **미리 안 보여주는 시험 문제**입니다.
  문제 일부를 금고에 넣어 두고, 공부가 다 끝난 뒤에만 꺼내서 시험을 봅니다.
  우리는 실패 사례 46건을 모은 뒤 무작위(시드 42)로 나눠 32건은 공부용,
  14건은 금고행으로 정했습니다. 그리고 이 분할을 룰 개발보다 **먼저**
  git 커밋으로 못 박았습니다(사전등록). 나중에 "시험 문제를 슬쩍
  바꾼 것 아니야?"라는 의심을 받지 않기 위해서입니다.

## ③ 우리 실험 이야기: 만점과 0점 사이

2026년 8월 25일 하루 동안 벌어진 일입니다.

먼저 GitHub 이슈 게시판과 Tiny Tapeout 공개 가이드 등을 뒤져서, 실제로
칩 플로우가 실패한 공개 사례 46건을 모았습니다. 각 사례에는 에러 로그 원문,
근본 원인, 해결책, 해결이 확인됐는지 여부가 붙어 있습니다. 예를 들어
"PDK(공장 재료 키트)를 설치만 하고 활성화를 안 해서 파일 경로가 안 잡힌"
사례(C-046)의 처방은 명령어 한 줄(`ciel enable`)이었습니다.

이 46건을 32건(공부용)과 14건(홀드아웃)으로 나눠 커밋하고, 실험 규칙서(protocol)를
**먼저 잠갔습니다(LOCK)**. 몇 점부터 합격인지, 무엇을 오답(miss)으로 세는지,
누가 채점하는지를 결과 확인 전에 전부 고정한 것입니다. 규칙서는 별도의
심판 엔진(Codex)의 심사를 세 차례 거쳐 확정했습니다 — 1차와 2차에서
"이 부분이 허술하다"는 지적을 총 8건 받아 고쳤고, 3차에서 승인됐습니다.

그다음, 공부용 32건만 보고 진단 룰 33개를 만들었습니다. "로그에
`Missing -liberty liberty_file`이 보이면 PDK 버전 호환 문제(C-008 계열)"
같은 식입니다. 연습문제 재대입 결과는 **32/32, 만점**. 소프트웨어 품질도
좋았습니다 — 테스트 커버리지 97%, 룰 형식 검사 통과, 출력 형식 위반 0건.
여기까지만 보면 성공이 눈앞인 것 같았습니다.

그리고 금고를 열었습니다.

홀드아웃 14건 중 정답 라벨이 유효한 사례가 12건, 그중 로그 원문이 있는
11건이 진짜 시험 문제가 되었습니다(규칙서의 최소 기준 10건을 넘겨 시험 성립).
사례당 단 1회 실행, 수정 후 재도전 금지. 결과는 — **0/11, 전패.
H3는 refuted(기각)**되었습니다.

내용을 뜯어 보면 이렇습니다. 11건 중 9건에서 의사는 "모르겠어요(unknown)"라고
정직하게 답했습니다. 엉터리 병명을 지어내지 않고요. 나머지 2건은 답을 내긴
했는데, 심판 Codex가 "원인이 달라요"라고 판정했습니다. C-018은 진짜 원인이
"부품을 너무 빽빽하게 채우는 설정(FP_CORE_UTIL) 때문에 클럭 버퍼를 넣을
공간이 부족했던 것"인데, 진단기는 그 설정도 버퍼도 짚지 못했습니다.
C-028은 메커니즘과 관련 부품 모두 빗나갔습니다. 채점 기준은 미리 정한 대로
"같은 실패 메커니즘 + 같은 관련 부품"을 둘 다 짚어야 정답 — 비슷하게만
말한 것은 오답입니다. 합격선은 hits ≥ ceil(0.60 × 11) = 7, 기각선은
hits < ceil(0.40 × 11) = 5. 0은 5에 한참 못 미쳤습니다.

혹시 공부용과 홀드아웃에 같은 계열 문제가 섞여 점수가 유리해지지 않았는지도
기계적으로 감사했습니다. 관련 사례로 표시된 것은 1건(C-028)뿐이었고,
그마저 오답이어서 이를 뺀 부분집합에서도 0/10 — 결론은 달라지지 않았습니다.

왜 이렇게 됐을까요? 홀드아웃의 실패들은 공부용과 **다른 계열**이었습니다.
PDK 구조가 바뀌어 생긴 문제, 기술 파일 불일치, 심지어 CPU 명령어(AVX-512)
때문에 프로그램이 죽은 환경 문제까지. 실패의 종류가 꼬리가 아주 긴
분포(**롱테일**)여서 — 감기, 배탈 같은 흔한 병만 적어 둔 대응표로는
처음 보는 희귀병 환자를 진단할 수 없었던 겁니다.

## ④ 배운 것

첫째, **연습 만점은 실력의 증거가 아닙니다.** 32/32와 0/11의 간극이 바로
과적합의 교과서적 모습입니다. 홀드아웃을 미리 커밋해 두지 않았다면, 우리는
"만점짜리 진단기"라고 자랑하며 엉터리 도구를 세상에 내놓을 뻔했습니다.

둘째, **소프트웨어 품질과 진단 능력은 서로 다른 축입니다.** 커버리지 97%에
형식 오류 0건인 잘 만들어진 프로그램도, 아는 것이 대응표 33줄뿐이면
새로운 문제 앞에서 무력합니다. "코드가 튼튼하다"와 "똑똑하다"는 별개입니다.

셋째, **"모른다"고 말하는 설계가 안전합니다.** 9건의 unknown 덕분에
오진(false positive)은 0건이었습니다. 확신 없는 의사가 아무 병명이나 던지면
환자(사용자)는 엉뚱한 수술을 하게 됩니다. 모르면 모른다고 말하는 도구는
틀린 확신을 주는 도구보다 훨씬 낫습니다.

넷째, **다음 수가 데이터에서 보입니다.** 대응표(룰)는 흔한 병에는 빠르고
정확하지만 롱테일에는 구조적으로 약합니다. 그렇다면 대응표에 없는 환자가
왔을 때 AI가 로그를 읽고 즉석에서 추리하는 **2층 진료실**을 얹으면 어떨까요?
이번 실험에서는 판정의 공정성을 위해 일부러 꺼 두었던 그 층의 부가 가치를
검증하는 것이 후속 가설(H3.1)의 자연스러운 후보입니다.
